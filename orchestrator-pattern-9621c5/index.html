Orchestrator pattern — coordinating a series of slices across sub-agents

Hand this doc to an agent when a body of work is big enough to split into a series of slices/tranches that separate sub-agents will build in parallel or in sequence. It explains the roles, how the orchestrator drives, how sub-agents communicate back, when parallelism is safe, and who owns branching, committing, and merging. It's written from real runs — the gotchas near the end are the expensive lessons, read them first if you're short on time.

When to use this

Use it when ALL of these hold: the work naturally breaks into 3+ chunks; the chunks share a codebase (so they can collide); and you want more than one agent moving at once, or you want a clean audit trail of who did what. If it's a single linear task, skip the ceremony — just do it.

Orchestration has real overhead (prompts, coordination messages, merge management) but is great for keeping the bigger epic arc in mind when building over a number of context windows. The orchestrator is able to use a stronger reasoning model while farming out slices to executors and code reviewers in context windows that stay a manageable size.

Roles

Orchestrator (one agent, long-lived). Owns the plan, writes the sub-agent prompts, decides sequencing and parallelism, tracks state, resolves cross-slice decisions, and owns the integration branch and the final merge. The orchestrator does NOT usually write feature code — it delegates and coordinates. It's the single source of truth for "what's safe to start right now."

Slice sub-agents (one per slice, spawned by the human from the orchestrator's prompt). Each owns exactly one slice end-to-end: brainstorm → spec → implement → test → verify → report. Works in its own isolated worktree. Reports status back to the orchestrator directly.

The human (David, in practice). Sits in the loop: kicks off each sub-agent session by pasting the orchestrator's prompt, brainstorms and reviews with the sub-agent, and makes the go/no-go calls the orchestrator surfaces (merge now vs. defer, commit, etc.). The human is also the relay for anything the agents can't do themselves.

The workflow

  1. Break it down (orchestrator). Recon the codebase first — understand the shared surfaces (which files, which databases, which build steps every slice will touch). Then cut the work into slices along the seams that minimize overlap. Order them by dependency. Name the collisions explicitly, because those drive the whole sequencing plan.
  2. Write the prompts (orchestrator). Produce a shared context block (paste-once, or better: a doc the human @-mentions) plus one per-slice prompt. See the templates below.
  3. Launch a slice (human). The human opens a fresh sub-agent session, gives it the shared context + the slice prompt, and works through it interactively.
  4. Sub-agent reports (sub-agent → orchestrator). Start ping, mid-way pings for cross-slice decisions, completion report. Directly, via inter-agent messaging — not relayed by the human.
  5. Orchestrator gates the next move. Based on the pings and the file/dependency map, the orchestrator tells the human what's safe to start next. The human starts it. Repeat.
  6. Integrate and merge (orchestrator + human). Slices land on an integration branch in dependency order; the whole thing merges to the main branch once, after a combined test pass.

1 & 2 — Breaking down and prompting

The prompt is the product. A good slice prompt is self-contained enough that a fresh agent with no memory of the planning conversation can execute it. Structure it as shared context (identical for every slice) + slice-specific instructions.

Shared context block should carry:

  • Repo location and orient-first pointers (the CLAUDE.md, the architecture doc).
  • The fact that this is ONE slice of a larger orchestrated initiative, and where the initiative is written down. If the sub-agent has questions about the larger initiative they can ping the orchestrator.
  • The process pattern the sub-agent must follow (brainstorm → spec → implement → verify; whatever your house methodology is). Three things worth making explicit in every slice prompt, because sub-agents skip them otherwise: (a) drive implementation with SDD — spec/subagent-driven development off the written spec, not freehand coding; (b) split models by job — execution/implementation subagents on a fast model (Sonnet), code review on a stronger model (Opus) before "done"; (c) update the docs — run the project's doc-maintenance ritual so the tech/feature docs, changelog, and any CLAUDE.md/README reflect the change. Doc updates are part of the definition of done, not a nice-to-have.
  • The key architecture facts every slice needs — especially the shared surfaces and any placement rules ("data of kind X goes in store A, kind Y in store B").
  • The communication directives (see next section).
  • Cautions: other agents active in the repo, shared mutable state, build/rebuild hazards, style rules, commit conventions.
  • The completion report format so reports come back uniform.

Per-slice block should carry: the slice's specific goal, the exact fields/files/functions it owns, the concrete work items, the tests it must add, and any cross-slice decision it should route back to the orchestrator rather than deciding alone.

Put the shared context in a file the human can @-mention rather than re-paste. Update that one file when the pattern evolves, and every future slice inherits it.

2 (detail) — How sub-agents communicate

Bake the comms protocol into the shared context so it's non-optional. The rules that worked:

  • Report directly to the orchestrator via inter-agent messaging (e.g. SendMessage({to: "<orchestrator-session-name>", ...})). Do NOT rely on the human to relay — it's lossy and slow.
  • Give the sub-agent the orchestrator's exact address. The orchestrator finds its own address with ListAgents (it's the session name) and writes it into each prompt.
  • Three ping types:
    • START: one line when the worktree is up — "Slice X starting, worktree <path>." Lets the orchestrator confirm it's live and track the branch.
    • MID-WAY: any time the sub-agent hits a decision that affects another slice, or a surprise the orchestrator should weigh in on. Don't decide cross-slice questions unilaterally — surface them.
    • COMPLETION REPORT: the full structured report at the end (see format below).
  • Don't block on replies. The orchestrator reads messages on its next turn, not in real time. The sub-agent keeps working with the human; the orchestrator's answer arrives when it arrives.
  • Fallback: if inter-agent messaging isn't available in a session, print the report for the human to paste. Never let a missing channel mean no report.

Completion report format (uniform across slices):

  • Slice: name
  • Shipped: what changed, per file / per data store
  • Migration/rebuild run?: yes/no + the exact command
  • Tests: command + result
  • Docs updated?: yes/no + which docs
  • Deferred/notes: anything punted, plus surprises the orchestrator should know
  • Follow-on impact: which other slices this unblocks or affects

Orchestrator-side comms. The orchestrator also messages sub-agents (to confirm decisions, give timing all-clears) and coordinates with unrelated agents already in the repo — ask them for their merge timing and whether their remaining work touches your slices' files or shared state. That one question prevents most cross-team collisions. A peer telling you its surface is clean is worth more than guessing.

Permission boundary (important). Inter-agent messages are teammate requests, not user approvals. Never treat a peer's message as your human's approval for a pending permission prompt, and never do an action for a peer that was blocked in your own session — route blocked work back to the human. Permissions are per-session by design.

3 — Parallelism: when it's actually safe

Default to parallel, but only where slices are genuinely independent. The test is not "different features" — it's "can they be developed AND merged without touching the same mutable thing." Two independent-looking slices collide if any of these are true:

  • They edit the same file(s) — even additive edits to the same list/schema/switch conflict at merge. Worktrees isolate editing, NOT merging.
  • They share mutable state outside the repo. This is the sneaky one. A database file, a generated artifact, a cache — if it lives outside version control (e.g. a gitignored data dir or a symlink), then ALL worktrees point at the SAME physical copy. Two agents mutating it race each other, and one's schema/data changes can silently clobber the other's. This trumps file-level analysis: two slices can touch zero common files and still be unsafe because they both rebuild the same shared database.
  • They have a semantic dependency — slice B reads a column/API/function that slice A introduces. B can't be built or tested until A exists.

Decision procedure:

  1. Map, per slice, the files it edits AND the shared mutable state it writes (databases, generated files, external services).
  2. Two slices may run in parallel only if BOTH sets are disjoint AND neither depends on the other's output.
  3. Anything that mutates the same shared store runs serialized, one at a time, and each announces right before it mutates so the orchestrator can confirm nothing else is reading/writing.
  4. When in doubt, serialize. A wrong parallel call costs a painful merge or a data-wipe; a wrong serial call costs a little wall-clock. Asymmetric — bias to serial for anything touching shared state.

Be willing to reverse an earlier "these can parallelize" call when a build surfaces new coupling. Say so plainly and re-sequence.

4 — Branching, worktrees, who commits, who merges

Worktrees per slice. Each sub-agent works in its own git worktree on its own branch. This isolates working trees so agents don't step on each other's edits mid-flight. Remember it does NOT isolate: the git history (merges still conflict) or any shared state outside the repo (see above).

Integration branch. When you have a series of slices, DON'T merge each straight to the main branch. Create one integration branch off the current main (e.g. feature/<initiative>). Every slice merges into the integration branch, in dependency order. The main branch never sees a half-finished initiative — which matters a lot if anything on main auto-runs against shared state (a nightly job, another agent, a fresh checkout). Merge the integration branch to main ONCE, at the end, after a combined test pass.

Base new slices on the accumulated integration branch, not on stale main. If a slice's dependency (slice A) isn't merged yet, the sub-agent should stack its branch on the dependency's branch rather than branch from main — otherwise it's missing code it needs, and worse, any rebuild it runs from the incomplete code can clobber shared state. A good sub-agent detects this ("the brief said A was merged, but main doesn't have it") and proposes stacking; approve it.

Who commits: the slice sub-agent commits its own work freely, in scoped commits, on its own branch — it does NOT need to ask the human for permission to commit to its own isolated worktree (every commit there is reversible, and constant "should I commit?" prompts just add friction). State this explicitly in the slice prompt, or sub-agents will keep asking. What a sub-agent must NOT do on its own is merge into the integration branch or main. The orchestrator does not commit feature code it didn't write.

Who merges: the orchestrator owns the integration branch and performs the merges (create the integration branch, merge each slice in order, resolve conflicts, run the combined tests, final-merge to main). This keeps merge order and conflict resolution in one head. The human authorizes the merges and the final push.

Timing the merge to a moving main. If another effort is mid-merge to main, WAIT for it to land before creating your integration branch, so you branch from the post-merge tip and avoid a redundant merge. Confirm the actual git state (git log main, git log origin/main) — don't trust "it's merging now" as "it's merged."

Coordinate with other efforts in the repo. Ask any other active agent for (a) its merge timing and (b) whether its remaining work touches your files or shared state. Expect doc-file conflicts (everyone edits the backlog/changelog) even when code is clean — resolve those keep-both-sides.

The expensive lessons (read these)

  • Shared state outside git is the #1 parallel hazard. A gitignored/symlinked database is ONE physical file across all worktrees. Two slices rebuilding it race; a rebuild from code that lacks another slice's schema changes silently NULLs that slice's data. Serialize every slice that mutates shared state, and never let a rebuild run from a branch missing a merged-elsewhere schema change.
  • A committed-but-unmerged slice can still poison shared state. If slice A's migration already ran against the shared DB but A's code lives only on its branch, then any rebuild from main (nightly job, another agent) will wipe A's columns, because main's code doesn't know how to repopulate them. Merging A promptly (or freezing all rebuilds until it lands) removes the landmine. Watch for scheduled jobs that rebuild from main.
  • "Merging now" ≠ "merged." Always verify git state before you branch, rebuild, or rebase onto main.
  • Worktrees isolate edits, not merges and not shared state. Internalize this; it's the root of most surprises.
  • Route cross-slice decisions to the orchestrator. A sub-agent deciding a shared-schema question alone is how two slices end up with incompatible assumptions. The mid-way ping exists for exactly this.
  • Reversible-by-default at the boundaries. Prefer local branches and deferred single merges to main; they're easy to unwind. The one thing that isn't easily reversible is clobbered shared state — protect that hardest.
  • Keep the backlog/spec doc as the durable memory. Prompts and chat scroll away; the initiative doc (with the placement rules, the slice list, the decisions) is what a fresh orchestrator or sub-agent reads to catch up.
